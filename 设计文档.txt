# 2. 项目核心定位

CampusOne 不定位为传统教务系统。

重点解决校园中大量分散的问题：

* 学生不知道事务在哪里办理
* 各类申请入口分散
* 审批进度无法追踪
* 教室、会议室、实验室预约不透明
* 校园报修处理效率低
* 校园通知容易遗漏
* 活动信息分散
* 大量校园规章需要人工查询
* 学生频繁咨询重复问题
* 教师和行政人员缺少统一工作台

系统最终形成：

```text
校园服务
+
事务审批
+
资源预约
+
校园报修
+
校园活动
+
统一消息
+
数据分析
+
AI Campus Agent
```

# 14. 请假审批业务

基础流程：

```text

↓

↓
辅导员审批
↓
完成
```

```text
学生
↓
班主任
↓
完成
```

如果：

```text
请假 > 3 天
```

可以设计：

```text
学生
↓
班主任
↓
辅导员
↓
学院负责人
↓

```

审批流程必须支持条件分支。

建议使用 Flowable。

# 21. 预约并发控制

这是项目技术亮点之一。

场景：

两个用户同时预约：

```text
实验室 305
9月8日
14:00-16:00
```

只能有一个成功。

必须处理：

```text
并发请求
+
数据库事务
+
Redis 分布式锁
```

推荐：

```text
Redisson Lock

resource:
campus:reservation:{roomId}:{date}:{slot}
```

同时数据库增加唯一约束。

不能只依赖前端按钮 disabled。

# 28. AI 报修分类

用户输入：

```text
宿舍空调不制冷，而且一直滴水。
```

AI 可以分析：

```text
故障类型：
空调维修

紧急程度：
中等

可能原因：
冷凝排水管堵塞
制冷剂不足
过滤网堵塞

推荐服务组：
暖通维修组
```

但 AI 不能直接决定危险性较高的维修处理。

AI 主要用于：

* 分类
* 信息提取
* 服务组推荐
* 文本总结

# 93. 页面设计禁止事项

13. 操作按钮颜色五颜六色。

# 94. 后端禁止事项

禁止：

1. Controller 写全部业务逻辑。
2. 所有接口只有 CRUD。
3. 没有事务。
4. 没有 RBAC。
5. 只做前端权限。
6. 使用用户传入 ID 决定个人数据范围。
7. 任意修改业务状态。
8. 不处理并发预约。
9. 不防重复提交。
10. 删除关键业务数据而不记录日志。
11. 数据库所有字段 varchar。
12. 一个 Service 数千行。
13. 没有统一异常。
14. 没有参数校验。
15. AI 直接访问数据库。
16. AI 越权访问业务数据。

# 101. 最终 AI 执行要求

从现在开始根据本设计文档实际开发系统。

开发过程中：

* 不要反复询问已明确需求。
* 遇到小型细节自行按照真实校园系统合理设计。
* 保持前后端字段、状态、接口一致。
* 每完成一个模块检查是否存在假按钮。
* 每完成一个业务模块验证完整业务链。
* 所有关键功能必须连接真实后端。
* 所有复杂状态必须通过 Service 状态机修改。
* 所有个人数据必须通过当前登录身份获取。
* 所有写操作必须校验权限。
* 所有高并发业务必须考虑并发安全。
* 所有 AI Tool 必须经过权限体系访问业务 Service。
* AI 不直接访问数据库。
* AI 不得越权。
* AI 写操作必须经过用户确认。
* UI 全局遵循本 Design System。
* 所有页面中文展示。
* 最终项目必须能够真实启动、登录、操作和完整演示。

如果需求没有明确某个辅助字段、次要页面或视觉细节，可以根据高校真实使用场景自行完善。

但是不得擅自改变：

```text
Vue3 + TypeScript

Spring Boot

CampusOne 产品定位

智慧校园服务型架构

RBAC 权限体系

审批工作流

预约并发模型

AI Campus Agent

RAG

整体 UI Design System
```

最终目标：

> 打造一个可以用于毕业设计答辩、个人作品集和 Java 全栈 / AI 应用岗位面试展示的高质量智慧校园综合服务平台。
