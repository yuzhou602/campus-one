# CampusOne 系统设计

本文说明 CampusOne 当前版本的真实设计。它区分“已经实现”“静态演示”和“后续规划”，避免把产品愿景误写成现有能力。

## 1. 产品目标与边界

CampusOne 面向高校学生、教师、辅导员、行政人员和校园服务人员，把分散的校园事务汇聚到一个入口。系统关注的是“用户今天需要办理什么”，不是把学校基础表做成通用 CRUD 后台。

当前核心闭环包括：

- 校园事务申请、分级审批、退回与催办；
- 校园资源查询、预约、审核和冲突控制；
- 校园报修、派单、接单、处理、确认和关闭；
- 校园活动浏览、报名、取消与签到；
- 校园通知发布、投递、阅读与消息中心；
- 按角色组织的首页、任务中心、数据中心和系统管理；
- Web 静态演示模式与真实 API 模式；
- UIKit iOS 客户端源码。

当前 AI 校园助手是规则回复和 SSE（Server-Sent Events，服务端单向流式推送）演示，不是已接入大模型、RAG 或工具调用的生产 Agent。知识库表已经预留，知识库管理接口尚未完成。完整 AI 能力属于后续演进，不属于 v1.x 的生产承诺。

## 2. 系统上下文

```text
学生 / 教师 / 辅导员 / 服务人员 / 管理员
                    │
          ┌─────────┴─────────┐
          │                   │
      Vue Web             UIKit iOS
          │                   │
          └─────────┬─────────┘
                    │ HTTPS / JSON / SSE
             Spring Boot API
                    │
       ┌────────────┼────────────┐
       │            │            │
     MySQL        Redis       文件目录
  业务与审计数据  缓存与分布式锁  开发环境附件
```

GitHub Pages 部署的是 Vue 静态演示版。它通过 Axios 演示适配器读取虚构数据，并把用户产生的演示记录写入浏览器 `localStorage`。Pages 不运行 Java、MySQL 或 Redis，因此不能承担多人共享的真实校园业务。

## 3. 参与者与权限

系统采用“角色权限 + 数据范围 + 资源归属”三层授权。

| 角色 | 主要职责 | 典型数据范围 |
| --- | --- | --- |
| `STUDENT` | 发起申请、预约、报修、活动报名、查看本人记录 | `SELF` |
| `TEACHER` | 使用校园服务、处理分配给本人的教师审批 | `COLLEGE`、`CLASS` |
| `COUNSELOR` | 处理职工审批、发布通知、组织活动 | `COLLEGE`、`CLASS` |
| `SERVICE` | 查看被分派工单、接单并推进维修 | 被分配的工单 |
| `ADMIN` | 预约审核、报修派单、运营数据、终审 | `ALL`、`COLLEGE`、`CLASS` |
| `SUPER_ADMIN` | 用户数据范围、系统级管理和全局权限 | `ALL` |

授权判断顺序：

1. JWT 验证身份与账号状态。
2. 控制器或切面验证角色。
3. 服务层按学院、班级或本人范围过滤数据。
4. 对详情和状态变更再次验证资源归属或当前处理人。
5. 更新语句携带旧状态条件，防止并发请求绕过流程。

前端菜单隐藏只负责用户体验，不承担安全职责。所有关键权限必须由后端再次验证。

## 4. 领域划分

| 领域 | 核心对象 | 负责的问题 |
| --- | --- | --- |
| 身份与权限 | `sys_user`、角色、权限、JWT、数据范围 | 谁可以进入系统、看到什么、操作什么 |
| 服务目录 | 服务事项定义 | 用户可以办理哪些事项、由谁首审 |
| 事务审批 | 申请、审批记录 | 申请如何路由、推进、退回、驳回和归档 |
| 资源预约 | 场地、预约 | 时段是否可用、是否需要审核、如何防止冲突 |
| 报修工单 | 工单、图片、评价 | 故障如何派单、处理、确认和关闭 |
| 校园活动 | 活动、报名记录 | 容量控制、报名、取消和签到 |
| 通知消息 | 通知、用户通知 | 面向全体或指定用户投递并记录已读状态 |
| 工作台与分析 | 首页、任务聚合、运营指标 | 按角色汇总今天需要关注的内容 |
| AI 助手 | SSE 对话原型、知识表预留 | 为未来的知识检索和业务工具调用提供入口 |

领域之间通过 ID 和服务层协作，不允许前端直接拼装跨领域权限结论。

## 5. 技术分层

### 5.1 Web 前端

```text
views        页面与用户流程
layouts      角色化导航和工作区外壳
stores       登录会话、应用状态、通知状态
api          按领域封装 HTTP 调用
types        前后端共享语义的 TypeScript 类型
demo         GitHub Pages 使用的 Axios 演示适配器
```

同一组页面运行在两种数据模式下：

- 正式模式：Axios 请求 `/api/v1`；
- 演示模式：Axios 使用本地 adapter，不连接真实后端。

两种模式必须遵守相同的响应形状、状态名称和角色规则。演示数据不能另行发明接口契约。

### 5.2 后端

```text
controller   HTTP 参数、身份入口、响应封装
service      业务规则、事务、权限和状态转换
mapper       MyBatis-Plus 查询与条件更新
entity       数据库存储模型
dto / vo     输入校验与对外展示模型
security     JWT、角色切面、当前用户上下文
config       缓存、异步、限流、安全响应头和 OpenAPI
```

控制器不直接决定复杂业务状态。审批、预约和报修的转换由服务层完成，并放在数据库事务中。

### 5.3 数据与基础设施

- MySQL 保存用户、业务单据、状态和审计记录。
- Redis 为缓存、活动报名锁和预约锁提供支撑。
- Redisson 为单个资源日期和活动提供分布式互斥。
- Flyway 从基线版本持续升级数据库结构和种子数据。
- 本地文件目录只适合开发环境；生产附件需要持久化对象存储。

## 6. 一致性策略

### 6.1 事务一致性

申请提交和审批步骤创建位于同一事务。报名记录与活动计数、预约创建与冲突检查、工单状态转换也由事务保护。

### 6.2 并发一致性

- 预约：Redis 锁按“资源 + 日期”串行化冲突检查；数据库仍保存业务终态。
- 活动：Redis 锁限制同一活动的并发报名，数据库唯一键防止同一用户重复报名，条件更新防止人数超额。
- 审批、预约审核、工单派发和状态推进：更新语句包含旧状态条件；受影响行数不是 1 时返回 `409`。

锁只能减少竞争窗口，数据库条件和唯一约束才是最后防线。

### 6.3 编号策略

申请、预约和报修使用“业务前缀 + 毫秒时间 + 随机后缀”的可读编号。数据库唯一键负责最终去重。内部关联始终使用数值主键，业务编号只用于展示和检索。

## 7. 关键设计取舍

### 自研轻量审批，而不是 Flowable

当前审批只有固定的两级路线：按服务事项选择教师或职工首审，再由管理员终审。自研审批记录更容易展示和测试，也降低部署复杂度。代价是暂不支持图形化流程、会签、动态条件分支和流程版本迁移。当流程种类和分支显著增加时，应再评估工作流引擎。

### 模块化单体，而不是微服务

当前规模下，Spring Boot 模块化单体可以共享事务、统一鉴权并降低运维成本。领域包保持边界，为未来拆分留下空间。只有当不同模块出现独立扩缩容、独立发布或团队边界时，才值得拆分服务。

### 服务目录代码定义 + 数据库外键镜像

v1.x 的服务项数量少、审批路线固定，因此代码注册表是 API 与审批路由的事实来源；数据库 `campus_service` 保留稳定 ID 和外键完整性。Flyway 迁移负责确保两者一致。未来如果增加可视化服务编排，应把事实来源迁移到数据库，并为配置引入版本和发布流程。

### 静态演示与真实系统共用页面

共用页面减少两套 UI 漂移，但要求演示 adapter 严格复制真实 API 契约。任何后端响应变化都必须同时更新 TypeScript 类型和演示适配器。

## 8. 已实现、受限实现与规划

| 能力 | 当前状态 | 说明 |
| --- | --- | --- |
| JWT 登录与刷新 | 已实现 | Access/Refresh Token，退出后加入黑名单 |
| RBAC 与数据范围 | 已实现 | 关键审批和预约审核使用组织范围 |
| 两级事务审批 | 已实现 | 首审、终审、驳回、退回、催办 |
| 预约冲突控制 | 已实现 | Redis 锁 + 数据库查询 + 乐观锁 |
| 报修工单闭环 | 已实现 | 提交、派单、接单、处理、确认、关闭 |
| 活动报名与签到 | 已实现 | 容量和重复报名控制 |
| 通知与消息中心 | 已实现 | 全体和指定用户投递 |
| 文件上传 | 受限实现 | 本地目录，限制类型、大小和文件签名 |
| iOS 客户端 | 源码交付 | Windows 环境未执行 Xcode 真机验证 |
| AI 助手 | 原型 | 规则回复和 SSE，不是生产大模型能力 |
| RAG / Tool Calling | 规划 | 数据表有预留，业务实现尚未完成 |
| RabbitMQ / Flowable / MinIO | 未采用 | 不应写成当前依赖 |

## 9. 非功能要求

- 安全：生产密钥只从环境变量读取；数据库和 Redis 不暴露公网；文件响应启用 `nosniff`。
- 可用性：所有列表分页；业务冲突返回可识别的 `409`；异步通知失败需要监控和补偿方案。
- 性能：列表查询避免逐行查询；常用状态、负责人和时间字段建立组合索引。
- 可维护性：状态名称、服务目录和 API 类型保持单一事实来源；数据库变化只通过 Flyway。
- 可观测性：保留操作日志；生产环境还需要指标、集中日志、链路标识和告警。
- 隐私：演示数据必须为虚构数据；生产环境需要最小化采集并制定数据保留策略。

## 10. 演进顺序

1. 完成通知领域统一、活动管理输入 DTO 和更多接口级测试。
2. 将生产文件存储迁移到对象存储，并增加附件归属和下载授权。
3. 增加审计事件、失败通知补偿、指标与告警。
4. 在真实知识库、权限过滤和工具白名单完成后，再接入大模型。
5. 只有流程配置需求超过轻量审批能力时，再引入工作流引擎。
